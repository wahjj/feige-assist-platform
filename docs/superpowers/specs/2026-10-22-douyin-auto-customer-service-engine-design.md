# 抖音商家自动客服引擎设计

## 1. 文档状态

- 日期：2026-10-22
- 项目类型：学习与作品集演示
- 首版形态：本地运行的客服引擎、HTTP API、消费者演示页与商家审核后台
- 目标平台：抖音电商商家
- 当前阶段：等待用户审阅设计文档

## 2. 产品目标

本项目为商家系统提供一个可接入的自动客服引擎。商家系统负责连接抖音消息通道，客服引擎负责理解消费者问题、调用业务工具、生成符合规则的回复，并在涉及售后成本或风险时生成审批单或转人工。

首版用一个完整的售后场景证明产品价值：

1. 消费者询问物流长时间没有更新。
2. 引擎识别意图并收集订单信息。
3. 引擎查询订单和物流。
4. 引擎解释物流状态并给出下一步方案。
5. 如果消费者要求补偿、退款或补发，引擎生成审批单。
6. 如果出现争议、高风险或系统无法可靠处理的情况，引擎转人工。

首版成功不以闲聊质量为主要评价标准，而以业务闭环、权限控制、可追溯性和商家系统接入能力为标准。

## 3. 目标用户与使用方式

### 3.1 商家系统

商家已有接收和发送抖音消费者消息的能力。它通过 HTTP API 把消费者消息交给客服引擎，并把引擎返回的回复发送给消费者。商家系统也负责提供经授权的订单、物流和售后业务接口。

### 3.2 消费者

消费者通过抖音与商家客服沟通。消费者可以直接提出物流、订单和售后问题，但消费者输入始终被视为不可信内容，不能改变系统权限和业务规则。

### 3.3 演示使用者

老师、招聘方或项目评审者可以通过消费者演示页和商家审核后台分别模拟消费者与商家运营人员，观察自动回复、审批、转人工和审计记录。

## 4. 首版范围

### 4.1 包含

- 单商家演示环境。
- 模拟的抖音商家订单、物流和售后数据。
- 文本消息处理。
- 物流延迟和物流未更新场景的完整处理闭环。
- 意图识别、缺失信息收集和结构化回复生成。
- 订单归属校验、订单查询和物流查询。
- 退款、补偿、补发等售后动作的审批流程。
- 自动转人工、人工接管和会话摘要。
- 完整审计日志。
- 商家适配器接口和模拟实现。
- OpenAPI/Swagger 文档。
- 轻量消费者聊天页与商家审核后台。
- 一条命令启动。
- 可重复运行的自动化测试和演示数据。

### 4.2 不包含

- 真实的抖音开放平台应用审核和 OAuth 商家授权。
- 真实资金退款、真实优惠券发放或真实补发订单。
- 图片、语音、视频和文件售后。
- 多商家计费、套餐、组织管理和运营分析大屏。
- 多轮模型自主规划器。
- 公网生产部署、域名、TLS 和高可用基础设施。
- 面向真实消费者开放的公开服务。

## 5. 核心设计原则

1. **模型只提供建议，策略引擎拥有决定权。** 模型可以识别意图、提取槽位、提出工具查询和生成回复草案，但不能直接执行订单状态或资金相关操作。
2. **业务动作必须经过确定性规则。** 自动回复、审批和转人工由可测试的代码决定，不能只依赖提示词。
3. **平台能力位于适配器之后。** 抖音相关能力不进入核心领域逻辑，首版用模拟适配器，未来替换为真实商家接口。
4. **所有关键动作可追溯。** 工具调用、策略命中、审批、转人工和状态变化都写入审计记录。
5. **失败时停止或转人工，不编造业务事实。** 查询不到订单、接口异常或模型输出不可用时，不生成虚假的订单、物流或退款结果。
6. **本地演示优先。** 默认启动不依赖真实平台账号，测试可以离线、稳定、重复执行。

## 6. 系统架构

首版采用模块化单体。一个 FastAPI 进程承载 API、业务编排、策略、审批、适配器和演示页；模块之间通过明确的 Python 接口和领域对象隔离。

```text
商家系统 / 消费者演示页 / 商家审核后台
        |
        v
FastAPI 接入层
鉴权 / 限流 / 请求校验 / 幂等
        |
        v
Conversation Orchestrator
        |
        +-- Model Gateway
        |   意图 / 槽位 / 工具建议 / 回复草案
        |
        +-- Tool Gateway
        |   白名单 / 参数校验 / 权限校验
        |
        +-- Policy Engine
        |   自动回复 / 审批 / 转人工
        |
        +-- Approval Service
        |   售后动作审批与执行
        |
        +-- Handoff Service
        |   摘要 / 优先级 / 人工接管
        |
        v
Douyin Merchant Adapter
        |
        v
SQLite
会话 / 消息 / 订单快照 / 审批 / 转人工 / 审计
```

### 6.1 逻辑模块

- `api`：HTTP 路由、鉴权、请求响应模型、幂等处理。
- `orchestration`：管理一轮消息的处理步骤和会话状态。
- `model`：模型提供方抽象、结构化输出解析和结果校验。
- `tools`：订单、物流和售后工具的白名单与调用编排。
- `policy`：自动处理边界、风险分类、金额与权限规则。
- `approvals`：售后动作申请、审批决定和执行。
- `handoffs`：转人工原因、摘要和接管流程。
- `adapters`：抖音商家业务能力和消息通道的抽象与模拟实现。
- `persistence`：SQLite 存储、事务和领域数据映射。
- `audit`：结构化审计事件。
- `web`：消费者聊天页、商家审核后台和后台鉴权。

### 6.2 技术约束

- Python 3.12。
- FastAPI 和 Pydantic 负责 API 与数据校验。
- SQLite 作为本地持久化数据库。
- 演示页使用简单服务端模板或原生 HTML/JavaScript，不引入独立前端构建链。
- 主启动方式为 `docker compose up --build`，容器启动时自动初始化数据库并载入演示数据。
- 可额外提供开发脚本简化本地 Python 调试，但作品集验收以 Docker Compose 命令为准。
- 模型通过 OpenAI 兼容接口抽象，可替换提供方。
- 默认测试使用确定性的 Fake Model Provider，不依赖外网和模型账号。
- 可选配置远程或本地模型提供方以展示真实自然语言理解。

## 7. 一轮消息处理流程

1. 商家系统创建会话，或在已有会话中提交消费者消息。
2. 接入层校验 API Key、请求结构、会话归属和 `Idempotency-Key`。
3. 编排器读取会话上下文并调用模型网关识别意图和槽位。
4. 编排器检查是否缺少必要信息；缺少时返回 `needs_information`。
5. 编排器只允许模型从工具白名单中选择查询动作。
6. 工具网关校验消费者、订单归属和参数，再调用商家适配器。
7. 模型基于工具结果生成结构化回复草案和拟议动作。
8. 策略引擎重新判断回复内容和业务动作是否允许：
   - 安全的信息查询与解释可自动回复。
   - 退款、补偿、补发等有成本或改变订单状态的动作生成审批单。
   - 争议、高风险、接口失败、订单归属不确定或权限不足转人工。
9. 引擎返回结构化结果并写入审计记录。
10. 商家系统发送自动回复，或把审批和人工待办展示给运营人员。

每轮最多执行 6 次工具调用，防止循环和失控查询。相同幂等键的重复请求返回第一次处理结果，不重复创建审批单或执行业务动作。

## 8. 业务工具与适配器边界

核心引擎只依赖抽象能力，不直接拼装抖音开放平台协议。

### 8.1 商家业务适配器

首版定义以下能力：

- 根据当前消费者标识和可选订单号提示查找订单。
- 根据订单 ID 查询订单详情。
- 根据订单 ID 查询物流状态和最近物流事件。
- 查询现有售后记录。
- 在审批通过后创建补发、退款或补偿售后单。

所有订单返回结果必须包含所属消费者标识。核心引擎在查询后再次校验订单归属，不能仅依赖适配器声明。

### 8.2 抖音平台适配器

未来真实接入层负责：

- 抖音商家 OAuth 和凭据管理。
- 消费者消息接收与回复发送。
- 抖音订单、物流和售后接口映射。
- 平台错误码、限流与签名处理。

首版用模拟实现返回固定但可验证的数据。适配器契约测试确保未来实现与模拟实现遵循相同语义。

## 9. 自动处理、审批与转人工规则

### 9.1 自动处理

以下情况可以由引擎直接回复：

- 查询当前消费者自己的订单和物流。
- 根据已知物流状态解释进度。
- 收集订单号后四位、问题描述等必要信息。
- 告知售后政策、处理时限和可选流程。
- 生成不改变订单或资金状态的建议。

### 9.2 必须审批

以下动作必须创建审批单，审批通过前不得调用执行工具：

- 退款。
- 补偿或现金等价权益。
- 补发商品。
- 其他会改变订单状态或产生商家成本的动作。

审批单包含动作类型、关联订单、建议金额、原因、证据摘要、申请者和幂等键。审批通过后只执行一次；执行失败时记录失败并转人工。

### 9.3 必须转人工

以下情况必须转人工：

- 订单归属无法确认或消费者要求查询他人订单。
- 出现退款争议、平台投诉、法律风险或人身安全风险。
- 消费者持续强烈不满，自动处理没有取得进展。
- 模型连续失败、输出不合规或工具调用超过限制。
- 关键业务接口不可用，且无法给出可靠信息。
- 审批执行失败或出现状态冲突。
- 消费者明确要求人工服务。

## 10. HTTP API 设计

所有接口位于 `/v1`，使用 JSON。商家通过 `Authorization: Bearer <api-key>` 接入。本地演示预置一个开发商家，API Key 只以哈希形式存储。

### 10.1 创建会话

`POST /v1/sessions`

请求包含商家侧消费者标识和可选会话元数据。响应返回内部会话 ID、初始状态和创建时间。

### 10.2 提交消费者消息

`POST /v1/sessions/{session_id}/messages`

请求包含消息文本和必填 `Idempotency-Key` 请求头。响应返回以下结果类型之一：

- `replied`：可直接发送给消费者的回复。
- `needs_information`：需要继续询问的信息。
- `approval_required`：已创建待审批售后动作。
- `handoff_required`：已创建人工转接待办。

响应同时包含消息 ID、当前会话状态、结构化载荷和用于串联日志与审计事件的 `trace_id`。

### 10.3 查询会话

`GET /v1/sessions/{session_id}`

返回会话状态、最近消息、当前待审批动作、转人工状态和会话摘要。

### 10.4 查询审批

`GET /v1/approvals?status=pending`

返回当前商家的待审批动作。商家审核后台通过服务端复用同一审批查询能力，不向浏览器暴露商家 API Key。

### 10.5 提交审批决定

`POST /v1/approvals/{approval_id}/decision`

请求包含 `approve` 或 `reject`、审批人标识和可选备注。只有 `pending` 状态可以处理。通过后进入执行流程，重复审批返回冲突错误。

### 10.6 转人工与接管

- `GET /v1/handoffs?status=pending`：查询待接管会话。
- `POST /v1/handoffs/{handoff_id}/takeover`：人工接管会话。

转人工结果包含原因、优先级、会话摘要和人工待办 ID。

### 10.7 商家审核后台

后台页面与外部商家 API 共用同一套审批、转人工和审计服务，不复制业务规则。

- `GET /admin/login`：显示本地审核员登录页。
- `POST /admin/login`：创建审核员服务端会话。
- `GET /admin/approvals`：待审批列表，显示动作类型、金额、风险和等待时间。
- `GET /admin/approvals/{approval_id}`：审批详情，显示消费者对话、订单摘要、物流证据和拟议动作。
- `POST /admin/approvals/{approval_id}/decision`：提交通过或拒绝决定。
- `GET /admin/handoffs`：待接管会话及风险原因。
- `POST /admin/handoffs/{handoff_id}/takeover`：审核员接管会话。
- `GET /admin/sessions/{session_id}`：查看会话详情和审计时间线。

后台使用服务端会话和 CSRF 防护，页面中不暴露商家 API Key。首版预置一个本地审核员账号，审核员标识会写入审批和接管记录；用户管理、角色权限、批量审批和规则配置不纳入首版。

## 11. 状态模型

### 11.1 会话状态

- `active`：自动客服正在处理。
- `needs_information`：等待消费者补充信息。
- `awaiting_approval`：等待商家审批。
- `awaiting_human`：等待人工接管。
- `human`：已由人工接管。
- `closed`：会话结束。

### 11.2 审批状态

- `pending`
- `approved`
- `rejected`
- `executing`
- `succeeded`
- `failed`

### 11.3 转人工状态

- `pending`
- `taken_over`
- `closed`

状态变化只能通过领域服务进行。审批冲突、重复接管和非法状态迁移返回 `409 Conflict`，不覆盖已有状态。

## 12. 数据模型

所有主键使用 UUID，金额使用整数分，时间使用 UTC。

- `merchants`：商家标识、显示名称、API Key 哈希、创建时间。
- `reviewers`：商家标识、审核员标识、显示名称、密码哈希和本地启用状态。
- `sessions`：商家、外部消费者标识、状态、摘要、创建和更新时间。
- `messages`：会话、角色、原始文本、处理结果、关联 `trace_id`、创建时间。
- `orders`：模拟订单、商家、消费者标识、金额、商品摘要和订单状态。
- `shipments`：订单、承运商、运单摘要、物流状态和最近事件时间。
- `approvals`：会话、订单、动作类型、金额、原因、证据、状态、审批人、幂等键。
- `handoffs`：会话、原因、优先级、摘要、状态、接管人。
- `audit_events`：事件 ID、会话、`trace_id`、事件类型、结构化载荷、时间。

持久层不保存模型密钥，不把完整支付凭证或无关个人信息写入审计日志。订单号、手机号和地址在日志与演示界面中脱敏展示。

## 13. 模型输出与提示边界

模型必须返回可校验的结构化对象，而不是自由文本直接执行。核心字段包括：

- 意图和置信度。
- 已提取及缺失的槽位。
- 拟调用工具及参数。
- 给消费者的回复草案。
- 拟议业务动作及理由。
- 是否需要人工处理。

模型输出不合法、调用未授权工具或尝试跳过审批时，工具网关和策略引擎拒绝执行。消费者消息中的“忽略规则”“直接退款”等内容没有系统指令权限。

## 14. 错误响应与降级

所有 API 使用统一错误结构：错误码、可读消息、请求 ID 和可选字段错误。

- `400`：请求无效或业务参数不完整。
- `401`：缺少或无效 API Key。
- `403`：无权访问该会话、订单或审批。
- `404`：资源不存在。
- `409`：幂等键复用了不同请求，或状态不允许当前操作。
- `422`：结构化数据校验失败。
- `429`：本地演示可预留限流响应。
- `503`：模型或业务适配器暂时不可用。

模型超时先有限重试一次；仍失败时使用安全话术并转人工。业务查询超时进行有限重试；仍失败时不生成业务事实。售后执行失败不自动重复退款或补发，而是标记失败并要求人工处理。

## 15. 安全与隐私

- API Key 只保存哈希，日志不输出完整凭据。
- 所有会话、订单和审批查询校验商家及消费者归属。
- 工具使用白名单，禁止模型访问任意 URL、SQL 或文件。
- 退款、补偿和补发必须经过审批，测试要求未审批执行次数为零。
- 审计日志过滤密钥、完整地址和无关个人信息。
- 对提示注入和越权请求使用专门的自动化测试覆盖。
- 演示数据全部为虚构数据。

## 16. 演示体验

演示系统分为两个入口：

1. **消费者聊天页**：显示预设订单和一段物流延迟对话，可以继续输入消息，展示自动回复、补充信息、审批等待和转人工。
2. **商家审核后台**：显示待审批动作、会话摘要、订单与物流证据、审计事件和转人工待办，允许审核员通过或拒绝售后动作，以及接管人工会话。

后台不是单向展示页。审核员可以在同一处完成证据核对和决定，后台操作通过领域服务更新审批状态；浏览器不能直接调用售后执行工具。

内置可重复场景：

- 正常物流解释并自动回复。
- 消费者要求补偿，生成审批单但不自动执行。
- 审批通过后调用模拟售后工具并记录结果。
- 订单号不匹配或消费者试图查询他人订单，被拒绝。
- 消费者明确要求人工或触发高风险规则，进入人工队列。
- 重复提交同一消息不会创建重复审批。

## 17. 测试策略

### 17.1 单元测试

- 意图和槽位缺失判断。
- 自动回复、审批和转人工策略矩阵。
- 金额、动作类型、订单归属和状态迁移规则。
- 幂等键和重复审批。

### 17.2 集成测试

- FastAPI 接口与 SQLite 事务。
- 模拟商家适配器的订单、物流和售后执行。
- 模型结构化输出失败、超时和无效工具请求。
- 审批通过后只执行一次。

### 17.3 契约测试

- 模拟适配器与未来抖音适配器必须满足相同接口语义。
- 订单查询结果包含消费者归属字段。
- 售后执行接口接受幂等键并返回稳定的成功、失败语义。

### 17.4 端到端测试

- 从创建会话到物流查询、自动回复和关闭。
- 从补偿请求到待审批、人工审批、执行和审计。
- 从风险请求到转人工、人工接管。
- 从无效订单到安全拒绝。
- 审核员登录后台、查看审批证据、通过或拒绝审批并看到状态更新。
- 审核员从后台接管待人工会话。
- 未登录或越权审核员无法查看和操作审批。

### 17.5 安全测试

- 尝试通过消费者文本绕过审批。
- 尝试查询他人订单。
- 尝试让模型访问非白名单工具。
- 检查日志和 API 响应中的敏感字段脱敏。

测试默认离线运行。使用 Fake Model Provider 和固定种子数据保证结果可重复；真实模型提供方只用于可选的人工体验验证。

## 18. 验收标准

首版完成后必须满足：

1. 在安装 Docker Compose 的全新本地环境通过 `docker compose up --build` 启动。
2. 演示页能完成物流延迟咨询的完整自动处理。
3. 商家审核后台可以展示待审批动作、对话、订单和物流证据。
4. 审核员可以通过或拒绝审批，审批结果和审核员标识被持久化。
5. 补偿或退款请求一定生成审批单，未审批前执行工具调用次数为零。
6. 审批通过后模拟售后动作只成功执行一次。
7. 商家审核后台可以展示并接管待转人工会话。
8. 高风险、越权和业务失败可以转人工。
9. 会话、审批和审计记录在服务重启后仍然存在。
10. 商家适配器可通过替换实现接入新的业务系统。
11. OpenAPI 文档能够说明主要接口和请求响应结构。
12. 自动化测试覆盖后台鉴权、审批、转人工、幂等和越权场景。
13. README 能说明作品集价值、系统边界、本地启动方法和模拟数据范围。

## 19. 未来扩展

后续可以在不重写核心规则的前提下增加：

- 真实抖音商家 OAuth 与消息通道。
- 多商家租户和凭据隔离。
- PostgreSQL、Redis 和异步任务队列。
- 图片和语音理解。
- 优惠券、物流拦截、改地址等更多业务工具。
- 知识库与商品信息检索。
- 人工客服工作台和实时协作。
- 指标、质检和运营分析。

首版只需要保证适配器、工具、策略和数据归属边界正确，不提前实现这些扩展。
